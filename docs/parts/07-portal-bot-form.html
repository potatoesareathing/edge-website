Part 6The portal, the chatbot and the form

The three most intricate parts of your site. The portal because it is genuinely advanced, the chatbot because people will misunderstand what it is, and the form because it is the only part handling real personal data — and the only part currently broken.

6.1  The dimensional portal

Hovering the Ask EDGE button tears an irregular opening in the page, through which a pixel-art world is visible. Clicking commits: the tear grows until that world is all there is. It reverses on the way back.

The central trick

The canvas draws ONLY the destination world

Everywhere outside the tear, it writes alpha 0 — fully transparent. Your actual page is simply still there underneath, showing through.

Nothing about the homepage is captured, copied or re-rendered. That is what keeps the whole effect to a single shape and one small program. A naive implementation would render both worlds and blend them; this renders one world with a hole-shaped mask.

What actually runs on the GPU

Shader

A small program that runs on the graphics chip, once per pixel, in parallel. Yours is written in GLSL and lives as a string in portal.js:50–128. It receives the pixel's position and a handful of values from JavaScript, and returns a colour and an opacity.

Uniform

A value passed from JavaScript to the shader, the same for every pixel in a frame. Yours are: uTex (the video frame), uRes (canvas size), uTexRes (video size), uCenter (where the tear opens), uProgress (0 closed to 1 fully open), uMaxR (radius needed to cover the screen), uTime.

uProgress is the one that matters. JavaScript eases it toward a target; the shader draws whatever that number says. That separation is why a hover can become a click mid-animation without anything restarting.

The shader's core, annotated:

float wob = fbm(vec2(cos(ang), sin(ang)) * 2.4 + uTime * 0.05);
// fbm = fractal noise. Fed the ANGLE around the centre, so the wobble
// varies around the rim rather than across the screen. uTime makes it drift.

float r = uProgress * uMaxR;                      // ideal radius right now
r *= 1.0 + (wob - 0.5) * 0.26 * (1.0 - uProgress * 0.8);
// Distort that radius by up to ±13%, and fade the distortion as it opens —
// so a small tear is ragged and a finished world is not permanently rippling.

float edge = 1.5 + 54.0 * (1.0 - uProgress);      // soft edge, sharpens as it grows
float mask = 1.0 - smoothstep(r - edge, r + edge, dist);
if (mask <= 0.002) discard;                       // outside the tear: draw nothing

Three finishing effects, all fading out via settle as the tear opens:

  • Refraction — near the rim the world is pulled toward the opening, the way something seen through a lens bends at the boundary.
  • Chromatic aberration — red, green and blue are sampled at very slightly different positions along the radius, a fraction of a percent. This is the artefact real lenses produce; it reads as physical rather than digital.
  • Rim light — pow(rim, 7.0) concentrates a thin white line right at the edge. Monochrome, no hue added, because the design system forbids colour in chrome.

The public API — and why it is reusable

You asked for a system that could later carry Players, Updates and Join into their own worlds. That is why portal.js knows nothing about the FAQ. It takes a video and an origin element and does its job.

EDGE_PORTAL.configure({ video, origin, volume })  // tell it where it leads
EDGE_PORTAL.peek(true|false)                      // small tear, for hover
EDGE_PORTAL.open({ video, origin, volume, onEnter })  // full transition
EDGE_PORTAL.close()                               // reverse it
EDGE_PORTAL.suspend()                             // hidden tab: stop everything
EDGE_PORTAL.isOpen()  /  EDGE_PORTAL.supported()

To add a second world later you would create another video, another destination section, and call the same four methods. Procedure 11.16 has the steps.

Five failures this code already survives

Each of these was a real bug. They are documented because the guards look like paranoia until you know why they exist.

FailureGuard
Visitor's device has no WebGL supported() returns false and commit() calls enter() directly (app.js:599). They go straight to the world with no effect. Nothing is broken, only plainer.
The video has not buffered yet open() checks readyState. If there is no decodable frame it holds the peek open and waits for loadeddata, with an 1,800ms cap. Opening onto an empty texture is what once made the transition look like nothing happened.
The animation loop stalls A 2,600ms timer forces the handover and snaps progress to 1. Without it a stalled loop leaves someone in a half-open portal with audio playing, no interface and no way back.
The world appeared upside down WebGL's first texture row is the bottom; the DOM's is the top. UNPACK_FLIP_Y_WEBGL is set at setup and re-asserted on every frame, because it is context state that anything else touching the GL context could reset.
Hover teleported people instantly There is no dwell timer. Hover peeks; only a click commits. Being teleported by a mouse path that happened to pass the corner is hostile.

The audio ramp

Your brief asked for the world's audio to rise smoothly to a maximum of 40%. That is volumeCeiling = 0.4, ramped over 900ms on hover and back down over 420ms.

Two details matter. The ramp runs on setInterval, not rAF, for the reason in 5.5. And sound() checks a gestured flag before making any noise — browsers block audio until the visitor has interacted with the page, so until then a hover opens the portal in silence rather than throwing an error.

The bug that hid here

The gesture flag originally listened for pointerdown, pointerup, keydown and touchstart — but not click. On some paths the volume snapped to full instead of ramping. If you ever add audio elsewhere, list every event that could count as an interaction.

The CSS bug that made the entire site unclickable

Worth its own heading because it is the most instructive failure in the project.

The world section is marked hidden in HTML. The hidden attribute works by the browser's own default stylesheet applying display: none — and any rule you write outranks the browser's defaults. A rule saying .world { display: flex } therefore defeated hidden entirely. The world stayed laid out, invisible but full-screen, on top of the page, swallowing every click and scroll.

The fix is now a global rule near the top of the stylesheet:

[hidden] { display: none !important; }
Do not delete that line

It looks like a stray one-liner. It is load-bearing for the entire site's interactivity, and it protects every future component that uses hidden — the roster view, the join success panel, the crew wrapper.

6.2  The chatbot, honestly described

It is not AI

It is a keyword matcher. It scores what someone typed against the keywords attached to each answer you wrote, and returns the best one. It never generates text. Every word it says is a word you wrote.

This was a deliberate engineering choice, and the reasoning applies to your future projects. A real language model needs an API key. A key shipped inside a public web page can be read by anyone viewing source and used to run up your bill — and there is no way to hide it without a backend. The matcher costs nothing, works offline, never invents an answer, and cannot be abused.

How the matching works

  1. Normalise — lowercase, strip punctuation, split into words.
  2. Drop filler — about 80 words carrying no meaning. Question words (what, how, when) are in the filler list deliberately: when they counted as keywords, "what is the weather today" matched "What is EDGE?" purely on the word "what".
  3. Stem — a crude suffix-stripper so "years" matches "year" and "casting" matches "cast". Applied to both sides so they meet in the middle.
  4. Score — +2 per word matching a keyword, +1 per word appearing in the question text, +3 if the typed text is nearly the whole question.
  5. Normalise by length — divide by the square root of the word count.
  6. Compare to the confidence bar (1.4). Above it, answer. Below it, say so honestly and offer the nearest questions instead of guessing.
Why square root, and why this is a good lesson

Dividing by the full word count punished natural phrasing far too hard: "i want to sign up" scored below a bare "join", because three of its words carried no signal. The square root still stops a long rambling question from beating a short precise one, but much more gently.

The general lesson: when a scoring system misbehaves, the fix is usually to change how you normalise, not to add special cases.

Changing the bot

You almost never edit faq-bot.js. To change what it knows, edit EDGE.faq.entries in content.js. Each entry:

{
  q: "How do I join?",
  a: "Fill in the Join form. Pick Member for events and socials, ...",
  keywords: ["join", "sign", "signup", "register", "apply", "become", "entry"]
}

Put in the words people actually type, including slang and likely misspellings. The existing entries already include "enrol" and "enroll", "csgo" and "cs2", "pubg" for BGMI. That is the level of care that makes the difference.

Every entry also renders as a plain expandable list underneath the chat, so nobody is ever stuck if the bot misunderstands — and so search engines can read your answers.

If you later want a real AI chatbot

You cannot do it safely from a static site. You would need a small backend that holds the key and forwards requests. That is a genuine project, not a config change. The current design is the right one until the club has a reason to outgrow it.

6.3  The join form — and why it is broken

What works

Two paths in one form. Member asks the basics; Roster adds the competitive questions. Which fields are required changes with the path, so validation is driven by a rule table (join.js:93) rather than by required attributes in the HTML — a hidden field with required would block submission with a message nobody can see.

The validation is careful: names allow any script plus spaces and apostrophes (\p{L} matches letters in every language, so it does not reject non-Latin names); phone must be a 10-digit Indian mobile starting 6–9; email must have a plausible shape. There is also a honeypot — an invisible field named company at index.html:174. A human never sees it, so any value means a bot. The bot is shown the normal success screen rather than being told it was caught.

What is broken

One signal does exist: join.js:359 prints a warning to the browser console on every page load:

[EDGE] The join form is not connected yet.
Paste your Supabase URL and anon key into js/content.js -> join.backend.supabase.

Nobody was looking at the console, which is why this went unnoticed. Part 12 teaches you to look.

The security model — the most important thing in your project

Once you connect Supabase, your anon key sits in content.js where anyone can read it. That is intended. What protects the data is not secrecy but a database rule.

Row Level Security (RLS)

A Postgres feature letting the database decide, per row and per operation, who may do what. Supabase publishes every table over a public REST API, so RLS is the only thing standing between your anon key and your data.

supabase-schema.sql creates exactly one policy:

create policy "public can register"
  on public.registrations
  for insert          -- INSERT only
  to anon             -- for anonymous visitors
  with check (true);

And deliberately creates no others. No select policy means reads are denied by default. No update policy means nobody can alter a submission. No delete policy means nobody can wipe your registrations. You read the data while signed in to the Supabase dashboard, which runs as the service role and bypasses RLS.

Get this wrong and you leak every student's phone number

Without that policy — or with a select policy added carelessly — anyone could take the key from your page and download every name, register number, phone number and email address you have collected.

The schema file ends with two curl commands to verify it. The insert must succeed; the select must come back as an empty list []. Run both before the site handles a single real registration. If the select returns rows, stop and fix it.

The database also re-validates everything the browser checked — phone shape, email shape, and that a roster application has a game and an in-game name. This is not redundancy. Client-side validation is a convenience for the person filling the form; it is not a guarantee, because anyone can POST directly at the API and skip your JavaScript entirely. The database constraints are the actual protection.
