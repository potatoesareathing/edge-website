Part 15Running this site without a subscription

What you have to manage, what each job actually requires, and which tools — free, paid, or none at all — are worth using for it. Written on the assumption that your Claude subscription ends and does not come back.

The short answer

You can run this site indefinitely with no AI at all. Two scripts in scripts/ do the work that judgement used to: one checks your content before you publish it, the other checks your database is not leaking. Neither needs an account, an internet connection, or a subscription.

AI is a convenience for the tedious parts, not a requirement for any of them.

15.2  The two scripts that replace judgement

These were written specifically so you would not need an AI for the two things that can actually hurt you: breaking the site, and leaking student data.

Before every commit

node scripts/check-content.js

Parses content.js. If you broke it, it prints the offending line with its neighbours and the three causes it is almost always one of. If you did not, it checks the things that fail quietly instead: dates in the wrong format, links missing https://, images that are not on disk, images heavy enough to hurt on mobile data, placeholder names still in the roster, FAQ entries with too few keywords, and keywords generic enough that one answer will start swallowing unrelated questions.

It also refuses a service_role key by decoding the token rather than trusting what the variable is called.

After any database change, and quarterly

bash scripts/verify-supabase.sh

Checks four things against your live project: an insert is accepted, a select comes back empty, an update is refused, a delete is refused. The select is the one that matters — your key is published in the page source by design, so if a select succeeds, anyone can download every student's phone number.

Why this matters more than any AI tool

An AI can write code for you. It cannot tell you whether your database is leaking right now, and it will confidently assure you things are fine without checking. These two scripts check. Run them and you do not need anyone's opinion.

What to actually do

  1. Install VS Code today, while you still have help available. Free, and it is the single biggest reduction in how often you break something.
  2. Let the subscription lapse. Run on the two scripts plus a free chatbot.
  3. If you hit something you cannot do — a new feature, a bug you cannot locate — buy one month of Cursor or Claude, do the work, cancel. This is far cheaper than holding a subscription for a site that changes twice a semester.
The rule that keeps you independent whichever you choose

Never apply a change you cannot explain. If a tool hands you code and you cannot say why it works, ask it to explain before you use it. A site held together by changes you do not understand is a site you cannot maintain — you will have swapped one dependency for another, and the next one may not be as easy to ask.

15.4  What to watch out for

Not requested, but these are the things most likely to go wrong for you specifically, ranked by how likely they are to actually bite.

#RiskWhy it is likelyWhat to do
1Registrations collected before the database is verified The form shows a success screen whether or not the data arrives anywhere. You would not find out at a club fair until afterwards. Run verify-supabase.sh and submit one real test registration before sharing the link. Check the row appears in the dashboard.
2Placeholder content going public PLAYER-01 and Full Name are still on the Players tab right now. The checker warns about this on every run. One afternoon with content.js. This matters more than any code change in this manual.
3The Supabase project is tied to a personal account When you graduate, the club's registration data goes with you, or is lost. Record which email owns it. Consider a club-owned account. Same for GitHub.
4Free-tier database paused for inactivity Supabase pauses free projects after about a week of no activity. The form then fails silently and submissions queue in visitors' browsers. Open the dashboard occasionally. Export the CSV monthly so a pause is never a loss.
5Huge unoptimised photos The obvious next step is adding real event photos straight from a phone. Resize to about 1600px first. The checker warns above 600 KB.
6Video source files lost Three -source.mp4 files are gitignored and exist only on your laptop. A disk failure loses them permanently. Copy them to cloud storage. This is a five-minute job you keep not doing.
7Someone "tidies up" a load-bearing line [hidden] { display: none !important; } looks like a stray one-liner. Deleting it makes the entire site unclickable. It is documented in ARCHITECTURE.md. Read that before letting anyone else edit the stylesheet.
8No error monitoring If the site breaks for visitors, nothing tells you. You find out from a complaint, or never. Open the live site on a real phone once a month and watch the console. That is the realistic substitute.
9Personal data handled casually You are collecting names, phone numbers and register numbers from students. Do not share exports. Delete them when finished. Check whether RUAS requires a privacy notice before collecting at scale.
10The GitHub account is a single point of failure Lose access and you lose the site and every backup at once. Two-factor authentication, recovery codes stored somewhere physical, and a second committee member with access.
