Part 13Things to understand before your next website

Concepts this project already taught you, made explicit so they transfer. Each one is stated as a working principle, not a definition, with the evidence from your own code.

13.1  Separation of concerns

Your site keeps content, appearance and behaviour in separate files. That is why you can update the leaderboard without touching a line of logic, and why the whole design was converted from colour to monochrome without breaking a single feature.

The test: to change one thing, how many files must you open? If a content change requires editing logic, the separation has failed.

13.2  One source of truth

Every piece of content lives in exactly one place. The leaderboard is in content.js and nowhere else. If the same fact lived in two files, they would eventually disagree, and the bug would be invisible until someone noticed the site contradicting itself.

Apply it everywhere: colours as CSS variables, not repeated hex codes. Dates in one format. One list of tab names (TABS in app.js) driving the router.

13.3  Components are just functions that build things

You do not need React to have components. postCard(p) takes data and returns a finished DOM node. Called ten times, you get ten cards. That is the idea; frameworks add lifecycle management and automatic updates on top of it.

The lesson: understand the pattern before you adopt the tool. People who learn React first often cannot explain what it is doing for them.

13.4  State is where bugs live

Your site has very little state, and it is deliberately confined: the current tab, the join path, the portal's progress. Each lives in one place with one owner.

The rule that follows: never store the same truth twice. The portal knows its progress; the CSS reads it. If both JavaScript and CSS each tracked "is the portal open", they would drift apart, and the resulting bug would be maddening.

13.5  Design for failure, because it will

This is the most valuable thing in your codebase. Count the fallbacks:

  • No WebGL → the world still opens, plainly.
  • Video will not load → the poster image stands in.
  • Reduced motion → every effect is off and nothing is downloaded.
  • Scroll observer never fires → a two-second timer shows everything anyway.
  • Portal stalls → a 2.6-second timer lands it rather than freezing part-open.
  • Network drops mid-submission → the row is queued and retried.
  • Instagram post URL missing → the card is skipped silently.
  • Google Fonts unreachable → fallback fonts.

The principle: for every feature, ask what happens when it fails, and make that outcome acceptable rather than catastrophic. A site that degrades is a site that keeps working for the person on the worst phone and the weakest connection — which, on a university campus, is a lot of people.

13.6  Never trust the client

Your form validates carefully in the browser and the database re-validates everything. That is not redundancy. Anyone can bypass your JavaScript entirely and POST straight at the API. Browser validation is a courtesy to the person filling the form; the database constraint is the guarantee.

Generalise it: any check that matters must happen somewhere the user cannot reach.

13.7  Security is about permissions, not secrecy

Your Supabase key is published and that is correct. What protects the data is a rule saying anonymous visitors may insert and may do nothing else.

The general form: assume anything in the frontend is public, because it is. Grant the minimum permission that makes the feature work, and nothing more. Your database has no select policy, no update policy and no delete policy — not because they were forgotten, but because each would be an unnecessary permission.

13.8  Every dependency is a liability

Your site has zero and will run untouched for years. A typical beginner project has hundreds, each an opportunity for breakage, abandonment or a security advisory.

The question to ask before adding anything: what does this do that thirty lines of my own code could not? Sometimes the honest answer justifies it. Often it does not.

13.9  Version control is not backup — it is time travel

Git lets you see exactly what you changed before committing, undo a specific change from weeks ago, and recover a file you deleted. Your fifteen commits each carry a message explaining why, which is how you will understand your own decisions in a year.

Habits worth keeping: commit small and often; write messages that explain the reasoning, not the diff; never commit something you have not looked at with git diff.

13.10  Performance is mostly about what you do not send

Your page is around 200 KB before the video is conditionally attached. The videos are 97% of the total, which is exactly why they are gated behind three checks.

The lesson: the fastest asset is the one never downloaded. Before optimising code, look at what you are shipping at all. One unoptimised photograph can outweigh your entire codebase.

13.11  Accessibility is not an extra

Your ARIA tabs, keyboard navigation, form labels and reduced-motion support cost very little and were built in from the start. Retrofitting them would have been a rewrite.

The cheapest rules: use real <button> elements; give every image an alt; label every input; make sure everything is reachable by Tab. That is most of the value for very little effort.

13.12  Technical debt, and the honest kind

Debt is a shortcut you take deliberately, knowing you will pay interest. Your project has some and it is documented, which is what makes it debt rather than rot: netlify.toml left in place, the register-number rule left permissive, the placeholder content, the portal's single-instance state.

The distinction: a known shortcut with a note is manageable. An unknown one is a trap waiting for someone who has forgotten. Write the note.

13.13  Write down why, not what

Your code comments explain reasoning: why the video src is attached in JavaScript, why the scoring divides by a square root, why rAF is not used for the audio ramp. The code already says what it does; only a comment can say why.

DESIGN.md goes further and records mistakes that were made and corrected. That is unusual and genuinely valuable — it is what stops the same mistake being made twice.

Part 14What to learn next

Prioritised by what would actually make you capable of maintaining and extending this site. Not a general web-development curriculum — most of that you do not need.

Level 1 — Must understand now

Without these you are still dependent. Aim for a few weeks.

TopicWhy, for your site specificallyHow to learn it
Browser DevTools The highest-leverage skill on this list. Console, Elements, Network. Without it you are guessing; with it you are diagnosing. Open your own site and inspect things for an hour. Break something deliberately and find it.
Git basics status, diff, add, commit, push, log, checkout, revert. This is your deployment and your undo. The first three chapters of the free Pro Git book. Then use it daily.
JavaScript objects and arrays Editing content.js safely. Where commas go, why quotes matter, nesting. MDN's "JavaScript first steps". You need the data half, not the whole language.
CSS selectors and specificity The single trap that has bitten this project twice. Fixing anything visual requires it. MDN on specificity, then practise in the Elements panel where the answer is visible.
Reading an error message They name the file and the line. Beginners skim them. Deliberately cause errors and read what you get.

Level 2 — Should learn soon

These let you add features rather than only maintain them. A couple of months.

TopicWhyHow
DOM manipulation createElement, textContent, append, querySelector. This is what every renderer in app.js is doing. Write a small renderer of your own — a "sponsors" section, say.
Events and listeners How every interaction works. Including delegation, which sound.js uses. Read initTabs() and sound.js line by line until both are obvious.
Flexbox and Grid Every layout in your stylesheet uses one or the other. Flexbox Froggy and Grid Garden — both free, both games, both about an hour.
Media queries Section 20 of your stylesheet is where all phone fixes go. Resize your browser and watch what changes.
HTTP basics Status codes, GET vs POST, headers. Needed to debug anything involving Supabase. MDN's HTTP overview, then read the Network tab on a real request.
SQL fundamentals select, insert, where, and what a constraint is. You need this to read your own registrations. SQLBolt — free, interactive, a few hours. Then query your own table.

When the club's needs grow past what the site does today.

Level 4 — Advanced

Genuine specialisms. Pursue out of interest, not obligation.

  • GLSL and shader programming — what portal.js is written in. The Book of Shaders is the standard introduction. Until then, treat that file as finished.
  • WebGL properly — buffers, textures, the render pipeline. WebGL Fundamentals.
  • Web performance — Core Web Vitals, the rendering pipeline, why animating layout properties is expensive.
  • Accessibility in depth — the WCAG guidelines, and actually testing with a screen reader.
  • Video encoding — ffmpeg filters, codecs, bitrate. Directly useful if the club keeps making cinematic assets.

A note on how to learn this

Use your own site as the textbook

You have a working, well-commented, real project that you care about. That is worth more than any tutorial, because every concept has something concrete to attach to.

The most effective exercise: pick one function in app.js each week and read it until you can explain every line aloud. There are about thirty. In under a year you would understand your entire codebase — which is a different and much better thing than having watched thirty hours of video.
