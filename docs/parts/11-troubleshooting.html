Part 12Troubleshooting: how to find a fault yourself

The instinct when something breaks is to describe the symptom to an AI and ask for a fix. That works until it doesn't, and it never teaches you anything. This part teaches the alternative: locate the fault before you try to fix it.

12.1  The discipline

Debugging is not guessing repeatedly. It is narrowing a search space. Every step should eliminate possibilities, and you should be able to say what you learned from each one.

  1. Reproduce it. Exactly what did you click, on what device, in what browser? A bug you cannot reproduce is one you cannot verify you fixed.
  2. Locate the layer. Which of the seven layers in 12.2 is it in? Most of your time should go here.
  3. Read the error. Error messages are precise. Beginners skim them; the message almost always names the file and the line.
  4. Form one hypothesis and test it. One at a time, or you will not know which change worked.
  5. Fix, verify, and write down what it was. A bug that recurs and is re-diagnosed from scratch has cost you twice.

12.3  Browser DevTools — the four tabs that matter

Press F12 (or Ctrl+Shift+I). This is the single most valuable tool you own and it is already installed.

TabWhat it showsUse it for
Console Errors, warnings, and anything your code logged. Look here first, always. Red text = JavaScript crashed. It names the file and line. Your site also writes deliberate messages here — the join form's "not connected yet" warning appears on every load right now.
Elements The live DOM, and every CSS rule applying to whatever you select, in priority order. Any "why does it look like that" question. Rules that lost on specificity appear struck through. You can edit values live to experiment — changes vanish on refresh, which makes it a safe sandbox.
Network Every file requested, its status code, size and timing. Reload with it open. Is the video actually downloading? Did the CSS load? Is the Supabase request being made, and what did it answer? Red rows are failures.
Application Stored data. Under Local Storage you will find edge_join_queue. Seeing whether registrations are stuck in the queue on this device — direct evidence of the form problem in 6.3.
On a phone you cannot press F12

Connect an Android phone by USB, open chrome://inspect on your laptop, and you get the full DevTools for the phone's browser. For iPhone, enable Web Inspector in Safari settings and use Safari on a Mac.

Failing that, resize your desktop browser window to phone width. It catches most layout problems, though not touch-specific or performance ones.

12.5  Diagnosing a CSS problem properly

CSS problems feel mysterious because nothing errors. The method removes the mystery:

  1. Right-click the misbehaving element → Inspect.
  2. The Styles panel lists every rule affecting it, strongest first.
  3. Find the property that is wrong. If your intended rule appears struck through, it lost on specificity — the winning rule is above it. Match its selector shape (4.6).
  4. If the property is not listed at all, your selector does not match. Check for a typo or a missing parent class.
  5. Edit the value directly in the panel to confirm your fix works, then make the same change in styles.css.
  6. Use the Computed tab to see the final value of everything, and the box-model diagram to see actual padding, border and margin.

12.6  The most likely error you will ever cause

A syntax error in content.js. It empties the entire site, which is alarming and completely recoverable.

Uncaught SyntaxError: Unexpected token '}'    content.js:241

Almost always one of three things:

  • A missing comma between two entries in an array.
  • An unescaped apostrophe inside a single-quoted string: 'don't' ends the string early. Use double quotes: "don't".
  • A missing closing bracket } or ].

The reported line number is where the parser noticed, which is often a line or two after the real mistake. Look just above it.

git diff js/content.js     # see exactly what you changed
git checkout -- js/content.js   # or: throw it all away and start again

12.7  Deciding whether it is your fault

TestWhat it tells you
Does it break in a private/incognito window? No → it is a cache or an extension on your machine, not a real bug.
Does it break in a different browser? No → a browser-specific issue, usually a feature one browser lacks.
Did it work at the last commit? git stash, reload, git stash pop. If the old version works, your change caused it — and git diff shows you exactly what you did.
Is the file reaching the browser at all? Network tab. A 404 is a path problem, not a code problem.
Is GitHub itself down? githubstatus.com. Rare, but it happens, and there is nothing to fix.

12.8  When you do ask for help

Asking well is a skill, and it is the same skill whether you are asking a person, a forum or an AI. Include:

  • What you expected and what happened instead.
  • The exact error text, copied, not described.
  • Which layer you have already ruled out, and how.
  • The relevant code, not the whole file.
  • What you already tried.

That list is not politeness. Writing it out solves a surprising share of problems before you finish — the act of stating precisely what you expected is often where the wrong assumption reveals itself.

The rule that makes you independent

Never apply a fix you do not understand. If something is suggested and you cannot say why it works, ask for the reasoning before applying it. A site held together by changes you cannot explain is a site you cannot maintain — and you will have simply traded one dependency for another.
