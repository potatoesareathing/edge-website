Part 15Checklists

Reusable, and written to be used rather than admired. The first four apply to this site; the last applies to whatever you build next.

15.1  Pre-deployment checklist

Before every git push. Two minutes.

  • Previewed locally (node serve.js) and the change looks right.
  • Console is clean — no new red errors. (The join-form warning is expected until 11.14 is done.)
  • Checked at phone width — resize the window to about 375px.
  • Clicked through all four tabs; none are blank.
  • If you touched the form: submitted once on both Member and Roster paths.
  • If you touched the FAQ: hovered the launcher, clicked in, came back out.
  • git diff read — you can explain every changed line.
  • No secrets, keys or personal data in the diff.
  • Commit message says why, not just what.

15.2  Update checklist

For content changes, which is most of what you will do.

  • Editing content.js, not a logic file — if not, be sure you need to.
  • Commas between every entry; quotes closed; brackets balanced.
  • Dates are YYYY-MM-DD.
  • New images optimised (under about 400 KB) and given alt text.
  • New links include https://.
  • Reloaded the preview — the section actually changed.
  • Nothing else broke: the site still renders everywhere.
  • Run 15.1 and push.

15.3  Backup checklist

Monthly, ten minutes.

  • git push — all local work is on GitHub.
  • git status shows nothing uncommitted that matters.
  • Supabase data exported to CSV and stored somewhere private.
  • Video source files (*-source.mp4) exist in cloud storage — these are not in git.
  • _archive-v1/ copied somewhere, if you still want it.
  • Original logo artwork backed up.
  • Once a semester: git bundle create edge-backup.bundle --all, stored off-machine.
  • Once a year: actually test a restore (8.4). An untested backup is a hope.

15.4  Security checklist

At launch, then quarterly.

  • RLS verified: the curl select in supabase-schema.sql returns []. Not "probably" — run it.
  • Only an insert policy exists on registrations. No select, update or delete policy.
  • The service role key appears nowhere in the repository. Search for it: git log -p | grep -i "service_role"
  • No passwords, tokens or personal data anywhere in git history.
  • GitHub account has two-factor authentication on, with recovery codes stored physically.
  • Still no innerHTML anywhere: grep -rn "innerHTML" js/ returns nothing.
  • [hidden] { display: none !important; } still present in styles.css.
  • HTTPS enforced — the live URL shows a padlock.
  • Exported registration data is stored privately and deleted when finished with.
  • Anyone who left the committee no longer has repository access.

15.5  Future-project checklist

Before writing a line of your next site.

Decide first

  • Who is this for, and on what device and connection will they use it?
  • What is the one thing it must do well?
  • Does it genuinely need a backend, or is static enough? Static is cheaper, faster and safer — start there and add only when forced.
  • What happens to it when you graduate or lose interest?

Set up before building

  • git init and a first commit before anything else.
  • A .gitignore written before the first commit, not after — history is permanent.
  • A README saying what it is and how to run it, written on day one.
  • Content separated from code from the start. Retrofitting this is painful.
  • Deployment working on day one, with a placeholder page. Deploying for the first time at the end is how launches get delayed.

While building

  • Commit small, commit often, explain why.
  • Test on a real phone regularly, not just a resized window.
  • Keep a running note of decisions and their reasons.
  • For every feature: what happens when it fails? Make that acceptable.
  • Resist dependencies. Each one needs a justification.
  • Real <button> elements, alt on images, labels on inputs — from the start.

Before launch

  • Works on a phone, on a slow connection.
  • Works with JavaScript slow or partially failed — does it degrade or collapse?
  • No secrets in frontend code.
  • Any collected personal data is protected by a server-side rule, not by obscurity.
  • Backups configured and tested.
  • Someone other than you can deploy it.

Part 16The EDGE cheat sheet

One page. Print it, or keep it open.

Deploy

git add -A && git commit -m "what changed" && git push

Live in about a minute. Then hard-refresh: Ctrl+Shift+R. Preview first with node serve.js → http://localhost:8790

Protect these

  • GitHub account potatoesareathing — two-factor on, recovery codes stored. Losing this loses the site.
  • Supabase service role key — never in any file, ever.
  • Video sources assets/video/*-source.mp4 — gitignored, not backed up. Copy them somewhere today.
  • Registration exports — real student data. Store privately, delete when done.

Backup

Code: git push (automatic).   Registrations: Supabase → Table Editor → Export CSV, monthly.   Full snapshot: git bundle create edge-backup.bundle --all, each semester.

When something breaks

  1. F12 → Console. Red error? It names the file and line.
  2. Section empty? Syntax error in content.js — missing comma or unclosed quote.
  3. Nothing clickable? An invisible element is covering the page. Check [hidden] { display: none !important; } is still in the stylesheet.
  4. Network tab → reload. Red rows = missing files (404) or a failing service.
  5. Looks wrong but no errors? Right-click → Inspect. Struck-through rules lost on specificity.
  6. Pushed but unchanged? Hard-refresh, then check the commit is on GitHub.
  7. Undo: git checkout -- path/to/file  ·  already pushed: git revert <hash>

Rules that must stay true

  • content.js loads first; portal.js before app.js.
  • Never innerHTML. Always textContent.
  • Never start an asset path with / — relative paths only.
  • Never add a blanket img[src*="edge-mark"] CSS rule.
  • Match selector weight when overriding CSS (table.board-table, not .board-table).
  • Only animate transform and opacity.
  • Never use requestAnimationFrame for something that must simply happen.
  • Never deploy by uploading a folder. Deploy with git push.
  • The logo is 398×333 and the wordmark 665×183. Neither is square.
  • A solid white fill means primary action and nothing else.

Do this first

Connect the form (Procedure 11.14). Until you do, every registration is written to the student's own browser and lost. Then verify RLS: the select test must return [], or anyone can download every student's phone number.
